1. Start Here

Dashboard application

Use cookie-authenticated /api/* endpoints. Requests need credentials: "include". This is the normal choice for the company dashboard.

Website tracking

Use a publishable API key with /v1/touches, /v1/identify, and /v1/checkout-sessions. It is safe to expose this key in browser code.

Trusted conversions

Use a secret API key from your server for orders, updates, refunds, reads, reports, and payment-provider integrations. Never expose it in frontend code.

Base URL

Local:       http://localhost:5000
Production:  https://api.yourdomain.com

Replace BASE_URL in the examples with the deployed API URL. Unless noted otherwise, send and receive JSON.

2. Authentication

2.1 Dashboard cookie authentication

Login or registration sets an HTTP-only cookie named user_token. JavaScript cannot read this cookie; the browser sends it automatically when credentials are enabled.

const response = await fetch(`${BASE_URL}/api/workspace/dashboard`, {
  credentials: "include"
});
const data = await response.json();

Axios equivalent:

const api = axios.create({
  baseURL: BASE_URL,
  withCredentials: true,
  headers: { "Content-Type": "application/json" }
});
RoleMeaning
company_adminCompany settings, team, sites, keys, connectors, reports, orders, and customer administration.
company_viewerRead-only dashboard access to team, locations, transactions, bookings, and reports where permitted.
platform_adminCross-workspace administration and support operations.

2.2 API-key authentication

Authorization: Bearer pk_live_xxxxxxxxx

// Alternative accepted header:
X-Api-Key: sk_live_xxxxxxxxx
KeyUseAllowed from browser?
pk_test_... / pk_live_...Tracking and optional conversion ingestionYes, from an allowed origin
sk_test_... / sk_live_...Reads, reports, refunds, edits, trusted ingestion, and server integrationsNo
Never send a secret key to the browser. Do not put it in React/Vue source, a public NEXT_PUBLIC_* variable, localStorage, sessionStorage, or a mobile app bundle.

The backend derives the workspace from the verified key. Do not send or trust a frontend-supplied workspaceId for /v1 requests.

3. Request and Response Conventions

3.1 Request headers

Content-Type: application/json
Accept: application/json
Authorization: Bearer <API_KEY>       // /v1 only when using a key
Cookie: user_token=...                  // browser-managed for /api

3.2 Standard error

{
  "message": "Human-readable error description"
}

Some errors also include code, details, or provider-specific information. Frontend code must use the HTTP status as the primary decision and display message as the fallback.

3.3 Pagination

{
  "data": [ ... ],
  "pagination": {
    "page": 1,
    "limit": 25,
    "total": 120,
    "pages": 5
  }
}

Use the exact pagination object returned by each endpoint. Send query parameters such as page and limit only where supported, and enforce a frontend maximum page size.

3.4 Money and dates

  • Amounts are represented in minor units: 9999 means 99.99 in a two-decimal currency. Always read the accompanying currency.
  • Dates are ISO timestamps unless an endpoint documents a date-only filter.
  • Reports use the workspace timezone. Do not silently convert date-only filters through the browser timezone.
  • Do not use JavaScript floating-point arithmetic for money.

4. Account and Session APIs

Base path: /api/auth. Registration, login, verification, forgot-password, and logout are public. The session check requires the cookie.

POST/api/auth/company/register

Creates a workspace and its initial admin user. Sets user_token and sends verification email.

{
  "name": "Acme Corp",
  "email": "admin@acme.com",
  "password": "StrongPassword123!",
  "adminName": "John Doe",
  "country": "US",
  "timezone": "America/New_York",
  "currency": "USD",
  "industry": "Ecommerce",
  "dataRegion": "us"
}

Required: name, email, password, country. Typical response: 201 with message, workspaceId, slug, and userId.

POST/api/auth/user/login

Authenticates a user and sets the session cookie.

{ "email": "admin@acme.com", "password": "StrongPassword123!" }

Typical response: 200 and { "message": "User verified" }.

POST/api/auth/verify-user

Activates the user/workspace using the email token.

{ "verifytoken": "64_character_verification_token" }

Legacy clients may also use GET /api/auth/verify-user?verifytoken=... only if the deployed route supports it; the mounted route is POST.

POST/api/auth/user/forgotpass

Starts password recovery. Send only an email.

{ "email": "admin@acme.com" }

POST/api/auth/user/reset-password alias: /api/auth/reset-password

Completes recovery using the reset token.

{ "token": "signed_reset_token", "newPassword": "NewStrongPassword123!" }

GET/api/auth/me

Cookie required Checks the current session.

{
  "message": "Token decoded",
  "decoded": {
    "id": "user-uuid",
    "role": "company_admin",
    "name": "John Doe",
    "email": "admin@acme.com",
    "workspaceId": "workspace-uuid",
    "iat": 1718000000,
    "exp": 1718604800
  }
}

POST/api/auth/logout

Clears the session cookie. Send credentials when calling from a browser.

6. Sites and API Keys

6.1 Site management

All site routes require an authenticated company_admin.

MethodEndpointUse
POST/api/sitesRegister a website.
GET/api/sitesList registered sites.
GET/PATCH/DELETE/api/sites/:idRead, edit, or delete a site.
POST/api/sites/:id/verify-domainVerify DNS TXT or meta tag ownership.
POST/api/sites/:id/verifyLegacy verification alias.

Typical site creation body:

{
  "domain": "shop.example.com",
  "verificationMethod": "dns_txt"
}

Supported verification methods: dns_txt and meta_tag. Live publishable keys tied to an unverified site are rejected.

6.2 API key management

MethodEndpointUse
POST/api/api-keysCreate a publishable or secret key.
GET/api/api-keysList key metadata; plaintext keys are not recoverable.
PATCH/api/api-keys/:idUpdate permitted metadata.
DELETE/api/api-keys/:idRevoke a key.
POST/api/api-keys/rotateReplace an active key without a gap.

Typical creation body:

{
  "name": "Website browser key",
  "type": "publishable",
  "mode": "test",
  "siteId": "site-uuid",
  "allowedOrigins": ["http://localhost:3000"],
  "rateLimitPerMin": 600
}
Show-once behavior: store the returned plaintext key immediately. The API stores only a hash, so a lost key must be rotated.

7. Browser and Server Integration API

Base path: /v1. These endpoints use API keys. Tracking calls are browser-safe with a publishable key; reads, edits, and refunds require a secret key or dashboard session as shown.

7.1 Record a page touch

POST/v1/touches publishable · browser

Records one marketing touch for an anonymous visitor. Only visitorId is required.

const params = new URLSearchParams(location.search);
await fetch(`${BASE_URL}/v1/touches`, {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "Authorization": `Bearer ${PUBLISHABLE_KEY}`
  },
  body: JSON.stringify({
    visitorId,
    source: params.get("utm_source"),
    medium: params.get("utm_medium"),
    campaign: params.get("utm_campaign"),
    term: params.get("utm_term"),
    content: params.get("utm_content"),
    referrer: document.referrer || null,
    landingPage: location.href,
    pageTitle: document.title,
    gclid: params.get("gclid"),
    fbclid: params.get("fbclid"),
    ttclid: params.get("ttclid"),
    msclkid: params.get("msclkid"),
    fbc: getCookie("_fbc"),
    fbp: getCookie("_fbp"),
    ga: getCookie("_ga")
  })
});

Typical response: 201 with id, touchId, visitorId, visitorRecordId, siteId, channel, and touchedAt. A deduplicated repeat may return 200.

7.2 Identify a visitor

POST/v1/identify publishable · browser

{
  "visitorId": "visitor-uuid",
  "email": "customer@example.com",
  "phone": "+14155552671",
  "externalId": "crm-customer-123"
}

Use when a visitor submits a form, signs in, or otherwise becomes identifiable. Typical response contains customerId, visitorId, visitorRecordId, touchIds, touchCount, and isNew.

7.3 Freeze a checkout or booking context

POST/v1/checkout-sessions publishable · browser

{
  "visitorId": "visitor-uuid",
  "expiresInMs": 7200000
}

Typical response:

{
  "checkoutSessionId": "session-uuid",
  "token": "cs_123456",
  "visitorId": "visitor-uuid",
  "touchIds": ["touch-1", "touch-2"],
  "touchCount": 2,
  "expiresAt": "2026-10-22T18:00:00.000Z"
}

Pass token into payment or booking metadata. This freezes the relevant touch set.

7.4 Create an order or conversion

POST/v1/orders or /v1/conversions publishable or secret

The two paths use the same handler. For trustworthy revenue, call from your server with a secret key or use a verified connector webhook.

8. Connectors and Webhooks

These are not frontend browser calls. Payment providers call these URLs directly. The frontend only creates/configures connectors and displays their status or webhook URL.

8.1 Provider webhook URLs

Preferred form:

POST /api/connectors/{type}/webhook/{connectorId}

Supported types: stripe, shopify, zenoti, razorpay, paypal, generic, woocommerce, and square.

Legacy/manual form:

POST /api/connectors/{type}/webhook?connectorId={connectorId}

The provider-specific signature or stored connector secret is verified by the backend. Do not attempt to call these with dashboard cookies or API keys.

10. Errors, CORS, and Rate Limits

StatusLikely meaningFrontend action
400Invalid body, date, enum, or provider payloadShow validation feedback; do not retry unchanged.
401Missing/invalid/expired cookie or API keyRefresh session or configuration.
403Wrong role/key type, origin rejected, workspace inactive, or unverified siteShow permission/setup guidance.
404Resource not found in the authenticated workspaceRefresh list or show not found.
409Duplicate or conflicting resourceUse the existing resource or change the idempotency identity.
422Replay or workflow cannot be completedShow the failure reason and manual action.
429API-key rate limit exceededHonor Retry-After; use backoff.
500Unexpected backend errorShow a safe message and report request context.
502External gateway/provider failureRetry carefully or ask for provider reconnection.

Rate-limit headers

X-RateLimit-Limit: 600
X-RateLimit-Remaining: 599
X-RateLimit-Reset: 1792684800
Retry-After: 12

CORS requirements

  • Dashboard requests need credentials and an allowed frontend origin.
  • Publishable-key browser calls need the exact origin in the key's allowedOrigins.
  • Live publishable calls require an Origin header.
  • Never solve CORS by exposing a secret key in the browser.

11. Recommended Frontend Flows

11.1 Dashboard startup

  1. Call GET /api/auth/me with credentials.
  2. If 401, show login; if 403, show account/workspace status.
  3. Load workspace settings and dashboard reports.
  4. Use the workspace timezone for date filters and labels.

11.2 Website tracking

  1. Create or retrieve a first-party visitor ID in local storage after consent.
  2. Send one POST /v1/touches per relevant page visit.
  3. Call POST /v1/identify when the visitor identifies themselves.
  4. Call POST /v1/checkout-sessions at checkout/booking start.
  5. Pass the returned token into payment or booking metadata.

11.3 Trusted payment conversion

  1. Browser obtains the checkout token.
  2. Payment system stores it in provider metadata.
  3. Provider calls the connector webhook, or your server calls POST /v1/orders with the secret key.
  4. Backend resolves identity and attribution idempotently.
  5. Frontend reads the resulting report through the dashboard session.

11.4 Retry policy

  • Retry network failures and 5xx/502 responses only when the operation is idempotent.
  • Always send a stable idempotency identity for orders, bookings, and refunds.
  • Do not retry 400, 401, or 403 without changing the request or credentials.
  • Back off on 429 using Retry-After.

12. Frontend Launch Checklist

  • Base URL is environment-configured and never hard-coded for production.
  • Dashboard fetch/Axios calls include credentials.
  • Publishable and secret keys are stored and used in the correct environments.
  • No secret key appears in browser bundles, source maps, or public environment variables.
  • Publishable key allowed origins match deployed site origins exactly.
  • Tracking runs only after the application's consent policy allows it.
  • Visitor IDs are stable and checkout tokens are passed to the payment/booking system.
  • Trusted orders, edits, and refunds use a server-side secret path or provider connector.
  • All conversion mutations use stable idempotency identities.
  • 401, 403, 409, 422, 429, 500, and 502 have intentional UI behavior.
  • Report date filters respect the workspace timezone.
  • Connector setup uses the returned connector-specific webhook URL.
  • Failed connector events show replay status and do not silently disappear.
  • Frontend API types or contract tests are updated when response shapes change.
  • Staging has tested login, tracking, checkout, payment webhook, reports, refund, and logout.
Important boundary: the browser is responsible for visitor tracking and dashboard presentation. Trust-sensitive revenue changes and provider credentials belong on a server or in verified connector flows.
