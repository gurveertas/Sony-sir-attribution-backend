1. Executive Summary

The received backend is a substantial product upgrade rather than a simple code rewrite. It keeps the main dashboard route families, but adds a more complete public integration API, stricter key permissions, connector lifecycle management, gateway integrations, webhook replay, support-access auditing, timezone-aware reporting, customer merging, and automated tests.

Recommendation: use the received version as the stronger base, but migrate through staging. The most important frontend risk is the new separation between browser-safe publishable keys and server-only secret keys.

Backend quality

The received repository passes 112 automated tests covering API keys, connectors, webhooks, support access, timezone logic, merging, and reports.

Frontend risk

Low to medium if the dashboard uses cookie-authenticated /api/* routes. High if browser code uses publishable keys for reads, refunds, or edits.

Operational risk

Environment variables, encryption, webhook URLs, and database compatibility must be verified before production rollout.

2.4 Rate limiting and key lifecycle

Keyed requests now receive rate-limit headers. Clients should understand:

X-RateLimit-Limit
X-RateLimit-Remaining
X-RateLimit-Reset
Retry-After   (returned for 429 responses)

Keys can be revoked or expired, have a mode (test or live), may be tied to a verified site, and can stop working immediately when a workspace is suspended or closed.

2.5 Connector and gateway management

The received version adds company-facing connector management and provider-specific gateway connection flows. It supports credential validation, encrypted credential storage, automatic webhook setup where supported, reconnect, disconnect, verification, and connector health.

Gateway-related endpoints include:

2.6 Webhook URL and reliability changes

The received version supports connector-specific webhook URLs:

/api/connectors/{type}/webhook/{connectorId}

It also preserves the older query-string form using ?connectorId=.... Webhook events are stored before processing, can be replayed after failure, and eventually can be marked dead after repeated failures.

2.7 Support access and auditing

Platform administrators can start temporary support sessions. Access is time-limited, workspace-scoped, audited, and PII-masked by default. Company administrators can view who accessed their data, when, and why.

2.8 Reporting, merging, and time handling

Reports now use the workspace timezone for date ranges, daily trends, “today”, and drill-down lists. The received tests cover daylight-saving changes and non-UTC zones.

Customer merging now moves relevant orders, bookings, visitors, identifiers, and attribution history while recalculating new-versus-returning status atomically.

2.9 Testing and documentation

The original project has no meaningful test script. The received project has a working Node test suite with 112 passing tests. It also adds an integration guide at docs/COMPANY_API_GUIDE.md and serves generated documentation from public/docs/index.html.

3. Frontend Changes Required

3.1 Dashboard requests

Dashboard requests must include the authentication cookie:

fetch(`${API}/api/workspace/reports/summary`, {
  credentials: "include"
});

For Axios, use withCredentials: true. Ensure the frontend origin is included in the backend's CORS allowlist.

3.2 Browser tracking

Browser tracking should use only a publishable key. It may call touches, identify, checkout sessions, and, if accepted by the product design, conversion ingestion. Configure the publishable key with the correct site origin.

Authorization: Bearer pk_live_xxxxx
Do not expose a secret key: secret keys must never be placed in frontend source, browser storage, public environment variables, or a mobile app bundle.

3.3 Reads, refunds, and edits

Audit frontend code for these operations:

  • GET /v1/orders, customers, bookings, and reports: use the dashboard cookie or a server-side secret-key proxy.
  • PATCH /v1/orders/:id and PATCH /v1/bookings/:id: move to server-side secret-key calls.
  • POST /v1/refunds: move to server-side secret-key calls.

3.4 Error handling

StatusMeaningFrontend behavior
401Missing, invalid, expired, or revoked authenticationRefresh login or key configuration
403Wrong key type, origin rejected, site unverified, or workspace inactiveShow a specific configuration or permission message
429Rate limit exceededRetry after the Retry-After delay
502External gateway failureShow retry/manual setup guidance

3.5 Connector UI

Update connector screens to support gateway catalogs, connection state, verification, reconnect, disconnect, provider-specific setup instructions, webhook URLs, event history, and replay actions.

3.6 Report date filters

Do not silently reinterpret date-only filters through the browser's local timezone. The backend uses the workspace timezone. Display the timezone in report controls when users could be confused by day boundaries.

3.7 New optional dashboard features

These are not required for basic compatibility but are now available:

  • Customer merge workflow
  • Connector event replay
  • Gateway connection setup
  • Support-access history
  • Connector health indicators

5. Deployment and Database Requirements

5.1 Environment variables

The received version expects a fuller environment configuration. Review .env.example and configure at least:

NODE_ENV
aPORT=5000
DATABASE_PUBLIC_URL
JWT_SECRET
RESEND_API_KEY
EMAIL_FROM
APP_API_URL
ENCRYPTION_KEY

Use PORT, not aPORT; the first line above is shown only as a visual label. The actual variable is PORT.

Encryption warning: set a stable production ENCRYPTION_KEY. Do not change it casually after gateway secrets have been stored.

5.2 Public API URL

APP_API_URL must be a public HTTPS URL when automatic gateway webhooks are used. Localhost and private IP addresses will not work with provider webhooks; use a secure tunnel for local testing.

5.3 Database and migrations

The migration directory names are similar between the two repositories, but the received version includes schema-dependent gateway and support-access features. Validate the schema against a staging database or backup before production deployment.

Never reset the production database during this comparison. Confirm migration status, back up data, apply migrations, and run an end-to-end test afterward.

5.4 CORS and cookies

Confirm that the deployed frontend origin is present in the backend allowlist. For cross-origin cookies, the deployment must also use compatible HTTPS, cookie settings, and credentials-enabled requests.

6. Remaining Gaps and Disadvantages

6.1 Publishable-key order forgery

Orders posted directly from the browser can still be forged by a visitor. For trustworthy revenue, send orders from your server using a secret key or rely on a verified payment gateway webhook.

6.2 Documentation is not a substitute for contract tests

The received version includes extensive documentation, but response examples should still be verified against the running backend. Keep frontend contract tests for the fields and statuses the UI depends on.

6.3 Tests do not prove production readiness

The passing tests do not fully prove production database migration safety, real gateway credentials, email delivery, deployment proxy behavior, browser behavior on the deployed domains, or frontend compatibility.

6.4 External gateway dependency

Gateway APIs, credentials, provider signature formats, and webhook delivery remain operational dependencies. Add monitoring and alerting for failed events and connector health.

6.5 Rate limits may need tuning

The documented default is approximately 600 requests per minute for new keys, with per-key configuration. High-volume websites may need a larger limit, batching, or client-side throttling.

6.6 Support access needs governance

Support-access functionality is valuable, but production use should define approval rules, retention, alerting, and who can request unmasked PII.

7. Recommended Migration Plan

  1. Back up the database and create a staging copy.
  2. Install the received backend dependencies and confirm the test suite passes.
  3. Populate all required environment variables, especially JWT_SECRET, APP_API_URL, and ENCRYPTION_KEY.
  4. Check migration status against staging and apply only the required migrations.
  5. Inventory frontend calls to /v1, especially reads, refunds, and edits.
  6. Move secret-key operations behind a trusted server boundary.
  7. Verify dashboard calls send cookies with credentials.
  8. Update publishable-key allowed origins and site verification flow.
  9. Update connector setup to use the returned connector-specific webhook URL.
  10. Add handling for 401, 403, 429, 502, connector failures, and replay states.
  11. Run a staging flow: tracking, identify, checkout token, payment webhook, order, report, refund, and connector replay.
  12. Deploy with monitoring for authentication failures, rate limits, webhook failures, and encryption errors.
